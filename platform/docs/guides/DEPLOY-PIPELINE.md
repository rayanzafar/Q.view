# خطّ النشر إلى staging — الطريق الواحد

**القاعدة: النشر يتم بأمرٍ واحد لا غير.** كل طريقٍ آخر ممنوع ومحروس بالخطّاف. كُتب هذا
الدليل بعد حادثة 2026-08-11 (التقرير الكامل: `../reference/INCIDENT-2026-08-11-railway-down.md`)
التي أسقطت بيئة staging ~25 دقيقة لأن النشر وثق بحال ربط الطرفية فوقع على خدمة قاعدة البيانات.

```sh
cd platform
export SANAD_RELEASE=1
npm run deploy
```

## ماذا يفعل الأمر (scripts/deploy.mjs) — سبع خطوات لا تُتخطّى صامتةً

1. **شروط مسبقة**: جلسة إطلاق معلنة (`SANAD_RELEASE=1`)، التشغيل من `platform/`، شجرة git
   نظيفة (`--allow-dirty` للتجاوز الواعي). يقرأ حال ربط الطرفية **للتحذير فقط** — النشر
   نفسه لا يعتمد عليه أبداً.
2. **البوابات**: المعجم + الوثائق + الحزمة كاملة (`--skip-gates` لإعادة نشر شجرةٍ سبق
   التحقق منها — يُسجَّل صراحةً).
3. **نسخة احتياطية قبل كل نشر** (لا عند الترحيلات وحدها): `pg-backup.sh` عبر
   `railway run --service Postgres` بحقن `DATABASE_PUBLIC_URL` (المضيف الداخلي غير مبلوغ
   من بيئة التطوير). تُرفض نسخةٌ أصغر من كيلوبايت.
4. **النشر**: `railway up --detach --service <معرّف خدمة التطبيق> --environment <معرّف البيئة>` —
   **بالمعرّف الفريد لا بالاسم**: اسم المشروع يساوي اسم خدمة التطبيق («sanad-staging»)
   فتكذب فحوص الأسماء، والمعرّفات لا تكذب.
5. **انتظار `/ready` بمعرّف النشرة** حتى سبع دقائق: قبل الرفع يكتب الخطُّ `.build-id` (التزام git + طابع زمني؛ مُهمَل من git، مشحونٌ مع الصورة) ويعلنه الخادم في `/ready`؛ «جاهز» وحدها لا تكفي لأن الحاوية القديمة تبقى تجيب أثناء التبديل — وبهذا انطلق المسحُ الحي مرةً على القديمة وأنذر كذباً (v5.58). النقطة «·» في المخرجات تعني: القديمة ما زالت تجيب (الترحيلة الفاشلة توقف الإقلاع عمداً — راجع boot.sh).
6. **فحص سجلّات الإقلاع**: الترحيلات طُبّقت، ولا «فشلت الترحيلة».
7. **المسح الحي** بالأدوار المبذورة السبعة (KI-028) — أي انحرافٍ يُفشل الأمر.

## الممنوعات — ولماذا (يحرسها `scripts/hooks/pre-guard.mjs` منعاً لا يفتحه مفتاح الإطلاق)

| الأمر | لماذا ممنوع |
|---|---|
| `railway up` المباشر | ينشر على **الخدمة المربوطة** أياً كانت — وهكذا وقع التطبيق فوق قاعدة البيانات. الطريق: `npm run deploy`. |
| `railway down` | يزيل النشرة **النشطة** للخدمة المربوطة — أزال نشرة قاعدة البيانات الحية فسقطت البيئة. |
| `railway redeploy` | يعيد **آخر لقطة** لا مصدر الخدمة — أعاد اللقطة الفاسدة مرتين أثناء الحادثة. |
| ربط الطرفية بخدمة Postgres (`railway service/link`) | حال الربط سلاحٌ صامت: يبقى في `~/.railway/config.json` خارج git ويغيّر هدف كل أمرٍ تالٍ. |
| `railway variables --set` بلا `--service` صريح | يقع على الخدمة المربوطة أياً كانت. |
| `railway rollback` | **أمرٌ لا وجود له** في الطرفية — ذُكر خطأً في وثائق قديمة. |

## قراءة قاعدة البيانات بلا لمس الربط

```sh
export SANAD_RELEASE=1
railway run --service Postgres -- sh -c 'DATABASE_URL="$DATABASE_PUBLIC_URL" psql "$DATABASE_URL" -tAc "SELECT 1"'
```
حقنُ بيئةٍ لا ربط — ولا يغيّر حال الطرفية. (المضيف الداخلي `postgres.railway.internal`
غير مبلوغ من بيئة التطوير؛ استعمل `DATABASE_PUBLIC_URL` دائماً.)

## التراجع عن نشرةٍ فاسدة — بلا down/redeploy أبداً

1. **لوحة Railway**: الخدمة sanad-staging ▸ Deployments ▸ النشرة السابقة الخضراء ▸ **Redeploy**
   (زرّ اللوحة يعيد تلك النشرة بعينها — بخلاف أمر الطرفية).
2. **إعادة النشر من مصدر الخدمة**: تحديثُ متغيّرٍ يعيد البناء من مصدر الخدمة المضبوط لا من
   آخر لقطة — هذا ما أنقذ قاعدة البيانات في الحادثة:
   `railway variables --set "SANAD_RECOVERY_STAMP=<طابع>" --service <الخدمة>`
3. **البيانات**: `docs/guides/ROLLBACK.md` + النسخ في `data/backups/` + أرشيف PITR
   (حاوية Postgres-PITR).

## متغيّرات البيئة التي يجب أن تكون صحيحة على خدمة التطبيق

`PLATFORM_URL=https://staging.os.evcsol.com` — روابط رسائل البريد تُبنى منه؛ تركُه على
افتراضه المحلي يجعل كل زرّ «افتح صفحتك» ميتاً (وقع فعلاً — والإقلاع الإنتاجي الآن يرفض
قناة إرسالٍ فعلية برابط محلي). ومعه متغيّرات القناة (`MAIL_TRANSPORT`, `SMTP_*`,
`MAIL_FROM`, قائمة السماح) — راجع `GO-LIVE.md`.
